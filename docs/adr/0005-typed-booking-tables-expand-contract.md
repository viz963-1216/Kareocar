# 預約與行程搬到正式資料表：擴充→遷移→收斂，保留 jsonb、去程／回程獨立成表

預約、去程／回程、行程、行程與預約關聯、取消紀錄，從 `app_state`（jsonb）搬到正式資料表（#43）。伺服器要判斷的欄位拆成正式欄位：狀態、承接機構、需求者、服務對象、接送時間、版本，以及行程的司機與車輛。前端模型的其他部分仍放在每列的 `data` jsonb，`state-load` 回給前端的形狀不變。去程／回程獨立一張表（每段的狀態、負責機構、所屬行程），讓跨機構排車（ADR 0004）能直接用資料庫權限規則（RLS）只對協力機構開放那一段。

切換分四步，每一步都能單獨合併、全綠：

1. **擴充**：建立新結構；資料庫觸發器在寫入 `app_state` 時同步寫到正式資料表。
2. **遷移讀取**：分批把讀取改接正式資料表，這段期間寫入仍走 `app_state`。
3. **遷移寫入**：同一種資料的所有寫入一次改完，避免舊路徑用過時資料覆蓋新表。
4. **收斂**：拿掉同步觸發器，刪掉 `app_state` 裡的這幾種資料。

預約事件、預約修改快照、服務證明留在 `app_state`，權限改成查正式資料表裡預約的承接機構。預約→服務對象、行程→車輛不設外鍵，因為服務對象和車輛仍在 `app_state`；行程→司機保留外鍵。

## Considered Options

- 一次切換（所有改動放在一個整合分支）：正式資料庫雖然沒有真實資料，但改動牽涉十幾支資料庫函式和 6 個端點，PR 大到沒辦法好好審查，出錯也很難找
- 全部正規化、不留 jsonb：前端模型要由伺服器組回來，工程量大太多、好處有限
- 去程／回程留在 jsonb：跨機構排車要讓協力機構只看到一段，在 jsonb 上很難用 RLS 擋
- 服務對象與車輛一起搬：範圍變兩倍，它們不是這次要解決的問題

## Consequences

- 新增會讀寫預約或行程的資料庫函式時，一律用正式資料表，不要再讀 `app_state` 的這兩種資料
- 同步期間兩邊必須一致，由整合測試比對
- baseline 裡沒在用的正式資料表另開單清理
